# codeunlimited 1.7 Performance and Evidence Design

## Objective

Version 1.7 makes large local histories practical to query and makes the
project's performance and savings claims reproducible. It must preserve the
1.6 audit results for the same records while reducing the cost of bounded and
full-history scans.

The measured 1.6 baseline on an Apple M4 with 16 GiB RAM is:

| Scenario | Corpus | Wall time | Maximum RSS |
|---|---:|---:|---:|
| Full audit | 30.2 GiB, 2,747,957 usage records | 20-21 s | 1.57 GiB |
| 30-day audit | same on-disk corpus | 19.4 s | 1.28 GiB |
| Project-scoped audit | same on-disk corpus | 18.9 s | 180 MiB |
| Doctor | same on-disk corpus | 18.4 s | 180 MiB |
| Four-request fixture | fixture corpus | less than 0.01 s | about 7 MiB |

The 30-day and project-scoped timings show that 1.6 filters after reading the
whole Codex history. The full-audit RSS shows that repeated project, session,
and model strings are too expensive at multi-million-record scale.

## Scope

The sprint delivers four connected changes:

1. Parser-level time and project filters.
2. A small incremental Codex file index for repeated scoped scans.
3. Compact sharing of repeated request metadata.
4. A local benchmark harness and an evidence protocol.

It does not add a database of prompts, cache prompt or response text, change
detector formulas, or claim causal savings from observational data.

## Chosen Architecture

### Query-aware scanning

Introduce a parser query value with these logical fields:

```rust
pub struct ScanOptions {
    pub project: Option<PathBuf>,
    pub since: Option<i64>,
    pub use_index: bool,
}
```

The CLI computes the audit cutoff before scanning and passes it to both
parsers. Parsers reject old records before constructing `Request` values.
Existing commands without a known cutoff use `since: None` and retain their
current result set.

Codex session paths normally contain `sessions/YYYY/MM/DD`, but a session file
can continue receiving records after its directory date. The path date is
therefore a discovery hint, never sufficient proof that a file is old. A file
is excluded before opening only when an unchanged index entry proves its
maximum recognized timestamp precedes the cutoff. Without such an entry the
file is opened and its records are filtered individually. Files in unknown
layouts follow the same conservative rule.

Claude project selection continues to use its direct project directory. The
timestamp cutoff moves into `parse_claude_file`, avoiding allocations for old
assistant records even when a file spans the cutoff.

### Incremental Codex file index

Repeated project-scoped scans use
`CODEUNLIMITED_HOME/codex-index-v1.json`. Each JSONL entry contains only:

- canonical file path;
- byte length and modification timestamp;
- normalized cwd keys observed in `turn_context` records;
- minimum and maximum recognized token timestamps.

It never stores prompts, responses, token events, or model names. File paths
and normalized cwd keys are local paths and therefore potentially identifying;
the privacy inventory states this explicitly. A matching path, length, and
modification timestamp makes an entry reusable. Changed or new files are
inspected again; deleted entries are removed. Size is part of the identity so
same-second appends are not missed.

For a scoped query, unchanged files whose cwd set cannot match the requested
project are skipped. Relevant files are still parsed from source, so the index
cannot make token accounting stale. A cached `max_ts` older than the cutoff
also permits a safe skip.

The index is an optimization, not user data. Missing, invalid, or unsupported
index content is rebuilt. Writes use the 1.6 atomic writer. A symlinked or
unwritable index produces a warning and the scan continues without caching;
the audit result must not depend on cache availability. The audit command gets
`--no-index`, which disables both reads and writes for read-only or diagnostic
runs. Version 1.7 enables the index only for `audit`; report, fix, init, delta,
and compare retain their 1.6 write behavior and parser wrappers.

### Compact request metadata

Change repeated `project`, `session`, and `model` request fields from owned
`String` values to shared immutable strings. Parsers create one shared session
value per file and reuse project/model values until metadata changes. Reports
and detectors continue to consume string slices, so JSON and human-readable
outputs remain stable.

This is intentionally smaller than introducing numeric IDs and a global
string-table API. If shared strings do not meet the full-audit memory target,
numeric interning belongs in a later focused change rather than expanding this
sprint silently.

### Scan observability

Parser results expose non-sensitive counters used by tests and benchmarks:

```rust
pub struct ScanStats {
    pub files_discovered: u64,
    pub files_opened: u64,
    pub files_skipped_by_date: u64,
    pub files_skipped_by_index: u64,
    pub usage_records: u64,
}
```

Counters never contain file paths or project names. Normal audit output does
not change. With `audit --json --scan-stats`, the existing JSON object gains a
top-level `scan` object containing these counters; without the flag, the 1.6
JSON shape remains unchanged. Tests also inspect `ScanStats` directly.

## Benchmark Harness

Create `scripts/benchmark_local.py` using the Python standard library. It
accepts a release binary, repeat count, optional project, and output path. It
runs fixture, full, bounded-time, no-index scoped, and warm-index scoped
scenarios, discarding finding/project output so local project names cannot
leak into benchmark results. Indexed benchmark runs use a temporary
`CODEUNLIMITED_HOME`; they do not delete or replace the user's normal index or
configuration.

The JSON result records:

- codeunlimited version and Git SHA;
- OS, architecture, and total memory;
- corpus bytes and JSONL file count;
- per-scenario wall-time samples, median, nearest-rank p95, and maximum RSS
  where the host exposes it;
- exit status and non-sensitive scan counters.

The script refuses to overwrite an existing output unless `--force` is
provided. A Markdown summary can be generated from the same JSON, but JSON is
the source of truth.

`docs/BENCHMARKING.md` documents two evidence levels:

1. Performance evidence: parsing speed, memory, and output equivalence.
2. Outcome evidence: matched real tasks comparing completed tasks per million
   input tokens, success rate, wall time, cache-read ratio, context growth, and
   retry rate.

Version 1.7 ships the first level and the protocol for the second. It describes
reclaim totals as estimates and before/after deltas as observations until a
controlled task trial exists.

## Correctness and Failure Semantics

- A query-aware scan and a post-filtered unbounded scan over the same fixture
  must produce identical ordered requests and rate-limit series.
- Unknown timestamps are excluded when `since` is set, matching 1.6 CLI
  behavior.
- Unknown Codex directory layouts are opened rather than pruned.
- Index corruption never changes results and never overwrites a symlink.
- Appends, truncation, deletion, and cwd changes invalidate the affected index
  entries.
- Cache write failure is non-fatal and visible as a warning.
- All arithmetic and detector accounting retain the 1.6 saturation and union
  rules.
- Benchmark failures are explicit: a scenario with a non-zero exit is recorded
  and makes the harness exit non-zero.

## Tests

TDD covers:

- unchanged old Codex files with indexed maximum timestamps are unopened for
  a bounded query;
- an unknown-layout file with a recent record remains visible;
- old Claude and Codex records are filtered before result construction;
- first scoped scan builds an index and the second skips unrelated files;
- size/mtime changes, truncation, and deletion invalidate index entries;
- corrupt and symlinked indices fall back without changing results;
- `--no-index` performs no index write;
- compact request metadata preserves detector/report output;
- the benchmark harness calculates median/p95, protects existing output, and
  suppresses audited command output;
- release metadata consistently reports 1.7.0.

The final gate remains format, Clippy with warnings denied, release tests,
release build, package verification, Python tests, Rust 1.82, RustSec,
actionlint, installed-package smoke tests, and Linux/macOS/Windows GitHub CI.

## Acceptance Targets

On the same Apple M4 / 16 GiB machine and 30.2 GiB corpus:

- indexed `audit --days 30` after one completed index build: at most 5 seconds
  and at most 350 MiB RSS;
- second project-scoped audit: at most 1 second and at most 200 MiB RSS;
- full audit: at most 20 seconds and at most 800 MiB RSS;
- fixture and bounded real-data outputs: semantically identical to 1.6;
- parser recognition remains 100% for the current 2,747,957 usage records;
- no prompts or responses appear in the index or benchmark artifacts.

Performance targets are acceptance evidence for this measured host, not
portable unit-test thresholds. CI verifies behavior and output equivalence,
not machine speed.

Development happens on `codex/v1.7-performance`, based on the final 1.6 head.

move together to 1.7.0. The sprint does not merge either pull request, publish
a crate, or create a tag.
