# codeunlimited next level: adaptive work runtime

Date: 2026-09-04. Planning baseline: v2.1 branch at `c7c9519`.
Status: broader roadmap, not a claim of implemented or benchmarked optimization.
The selected 2.2.0 delivery slice is defined in
[the delivery design](2026-09-04-v2.2-delivery-design.md): opt-in explicit packets
and complete-attempt accounting. Learned scheduling, automatic retrieval and
default-on savings claims remain behind the evidence gates below.
Decision owner: product owner delegated architectural choices to Codex.

## Product decision

Build a subscription-first work optimizer, not another general-purpose agent
and not a prompt-compression utility. Keep Claude Code and Codex responsible
for coding. Make the surrounding runtime reduce repeated discovery, repeated
verification narration, avoidable model calls, and poorly chosen work boundaries.

The flagship promise to earn is: **less total model work for the same accepted
repository change, with inspectable evidence and a safe fallback**.

Version 2.2 is an evidence-gated release, not a promise of a savings percentage.
The separate [DCR research proposal](../../research/2026-09-04-delta-conditioned-reasoning.md)
explores a possible scientific contribution without claiming established novelty
or delaying the evidence-first product path.
The initial wedge is multi-step repository maintenance: regression fixes,
related small changes, and repetitive test-driven migrations. Open-ended research,
historical audits, and ambiguous architectural redesign stay on the native path.
API adapters remain separate. Gemini, model routing, lower reasoning effort,
multi-agent swarms, fine-tuning, and a replacement coding engine are out of scope.

## What the existing evidence actually says

- v2.1 has bounded state, stable instructions, usage normalization, local safety
  tests, and optional API caching. It does not establish realized savings.
- The checked-in two-arm historical dataset has 918,904 control input tokens
  and 1,077,493 treatment tokens: **17.2585% more**, with 24 versus 39 requests.
  Its paired-task p-value is 0.1875; task segments within one growing session
  are also not independent randomized episodes. This is observational evidence.
- The reported 0.65M batched arm is promising but lacks equivalent exact
  request-level data and matched acceptance evidence. Do not relabel it v2.2.
- The runtime starts a fresh CLI for every increment; each CLI can make many
  model/tool calls internally. Queue entries currently contain only id/task.
  There is no explicit batch selection, dependency-aware context contract, or
  within-worker cost controller. A fresh process is not itself a saving.

Reproduction: `python3 scripts/analyze_paired_experiment.py
docs/experiments/paired-2026-09-04-session-boundary.json --json`.

## Alternatives and choice

| Approach | Main benefit | Main limitation | Decision |
| --- | --- | --- | --- |
| More cache tuning | Potentially cheaper repeated input on APIs | Does not remove work; subscription accounting differs | Retain 2.1, not the next core bet |
| Adaptive work runtime | Removes avoidable calls and repeated discovery while retaining native agents | Needs measured scheduling and state freshness | Selected |
| Own full tool-loop agent | Direct control over every model input | New sandbox, quality burden, API spend, weak subscription fit | Defer unless the native boundary is a measured bottleneck |

## Architecture

```text
Objective + acceptance contract
              |
       Local work planner <--------- usage + acceptance receipts
              |
  bounded work packet + relevant verified facts
              |
   native Claude Code / Codex worker
              |
       diff + local verification
              |
  commit validated state / preserve evidence / plan next packet
```

### 1. Task contract and work packets

Represent each unit with id, objective, dependency ids, component/file scope,
acceptance check ids, risk class, and required capabilities. User-authored scope
is authoritative; model-proposed refinements are validated, not new permissions.

One worker performs one bounded **packet**, which may contain several related
units. Group only dependency-compatible units sharing component, checks, and
required tools; split on risk/permission changes or independent objectives.
Preserve the existing fresh-process state boundary between packets. Do not add
session resume or persistent hidden conversation in 2.2.

Start with deterministic, explainable grouping. A user-declared group is usable
without fitting a model. Unknown task scope falls back to native handling; it
must not silently become restart-after-every-small-task. A native whole-objective
run is the escape hatch, with the same accounting and acceptance contract.

Later choose packet sizes from completed, comparable local episodes. Predict
end-to-end tokens, including startup, context rehydration, state serialization,
repair, and output. Choose a candidate only when its conservative predicted
advantage exceeds a configurable margin; otherwise retain the declared grouping.
Cold starts produce recommendations, not fabricated fitted parameters. No
universal seven-request rule and no additional LLM scheduler call per step.

### 2. Retrieval-ready repository facts

Build small, task-specific context packets using existing index/AST facilities
when available and targeted files otherwise. Do not build a second CodeGraph.
Selection starts with explicit files, changed symbols and acceptance checks;
missing or stale structural results fall back to source reads.

Retain exact identifiers, paths, commands, failure signatures, decisions,
unresolved alternatives, and provenance. Each reusable fact records its source
file digests and applicable dependency/configuration fingerprints. A digest
proves freshness, not truth; a passing check supports only its explicit scope.
Unknown dependencies invalidate conservatively. Changed files, lockfiles,
compiler configuration, test commands, or environment invalidate affected facts.

Keep hot state bounded; cold artifacts are retrieved on demand and never appended
wholesale. Before a new worker, deterministically check that task prerequisites,
acceptance contract, unresolved blockers, and evidence references are present.
This is a contract-completeness check, not proof of semantic sufficiency.
If the packet is insufficient, expand within budget or use the native path.
Do not spend another model call merely to certify each summary.

### 3. Local execution and bounded observations

Start with explicit helper commands for Git metadata, selected test execution,
compiler diagnostics, and known machine-readable reports. They run real programs
without LLM reasoning. Output includes exit status, parsed failures, truncation
flags, and an on-demand reference to full output. Unknown formats pass through
or expose bounded raw slices; never silently discard potentially relevant errors.

Keep command argv exact, retain native permission checks, and never automatically
rewrite arbitrary shell commands. Scope local artifacts to the run with size
limits and retention controls; do not publish logs, secrets, or source snippets.
Incremental verification is allowed during a packet; the full frozen acceptance
suite is mandatory at the final gate. Reuse test results only with a complete,
unchanged input fingerprint; otherwise rerun. No claims that a cache hit proves
the current patch correct.

Begin with helpers inside managed workers. A separately opt-in native-session
integration is a later packaging step, after measured benefit; no global config
or permission changes and no transparent interception of arbitrary open chats.

### 4. Usage ledger and failure-aware controller

Add a versioned, metadata-only execution ledger for task, packet, attempt, model,
CLI version, policy/configuration hashes, timestamps, observed counters, coverage,
and acceptance. Stream native events when supported, but retain terminal totals
as the authoritative scope when that is all the provider supplies. Never sum
cumulative snapshots, request deltas, and terminal totals as independent usage.

Include child agents, compaction, planning, retries, failed envelopes, timeout
attempts, and recovery when measurable. Partial or unavailable usage remains
explicitly incomplete, never zero. Do not sum reasoning counters twice when
already included in output. If coverage is incomplete, refuse a full savings
verdict and show observed subtotals only.

At safe packet boundaries stop on repeated failure, budget exhaustion, or stale
evidence. Larger packets can reduce startup and also increase repair cost;
measure both. Do not repeatedly kill a worker mid-edit to meet a token target.
Token budgets are admission/soft limits unless the provider exposes enforceable
per-call caps. Timeout/attempt caps are hard process controls; late usage reports
can overshoot a token budget and must be reported honestly.

## Metrics and release gates

Primary outcome, separately per provider/model: total provider-reported
transported input plus output across **all assigned attempts**, divided by the
number of accepted tasks. Failed work remains in the numerator; zero accepted
tasks is undefined/failure, never zero cost. Also report input and output separately.

For matched blocks report total token ratio on all assignments, success rates,
per-block differences and intervals. Short tasks, long episodes, and task families
must remain visible; do not hide regressions in a favorable grand average.

Secondary outcomes: observed subscription allowance per accepted task when
available and attributable; actual API bill/credit cost only for API experiments.
An API-rate estimate is not subscription spend. Rounded shared-account meters
produce intervals, not exact task attribution; resets, concurrent activity, or
missing measurements invalidate that quota comparison, not the token dataset.

Diagnostics: model requests/accepted task, repeated-read volume where observable,
startup/rehydration, repairs, packet sizes, and cache traffic. These are explanatory,
not headline savings. Do not sum the percentages from different optimizations.

Guardrails: identical frozen acceptance tests and task scope, no new security or
data-loss failures, and p95 completion latency reported with a provisional +15%
regression threshold. Ad hoc human rescue is logged and not counted as an
unassisted successful run.

Product target, not forecast: **at least 25% fewer total tokens on the target
workload**, with a paired 95% interval excluding zero saving and no observed
acceptance regressions in the release sample. Seek 40% on long repetitive work
only as a stretch hypothesis. A small sample cannot establish zero quality loss
or a tight non-inferiority margin; report quality uncertainty and expand testing
before a broad default-on rollout. Failure to meet the target means keep the
feature experimental or remove it, not adjust the denominator or claim.

## Experiment ladder: spend only after cheap gates

1. Offline: synthetic protocol traces, immutable paired accounting, stale-fact
   challenges, lost-identifier tests, adversarial output, timeout and recovery.
   Replay describes overhead opportunities, not a causal counterfactual.
2. Calibration pilot: four matched episodes, native versus the smallest candidate,
   same provider/model/effort/tools, eight arm executions. Pre-authorize budget
   before any live call. Suggested first ceiling: eight arm executions, ten-minute
   timeout per worker, 2M total observed-token admission limit; the token cap is
   soft and internal requests can be numerous. Record overruns and stop new work.
   This is feasibility/calibration, not significance or a release claim.
3. Freeze candidate and protocol after pilot. Hold out 24 independent episode
   blocks across three authorized repositories and short/medium/long horizons
   (4/12/24 related work units). These are proposed sizes; confirm adequacy using
   pilot variance and quality precision before spending. Randomize AB/BA order,
   isolate worktrees and native memory where supported, and record cache state.
   No policy tuning on holdout data. Native control keeps normal compaction and
   competent task scoping; never manufacture a weak always-restart baseline.
4. Ablate packets, retrieved facts, and local output helpers on a smaller frozen
   diagnostic set. Compare arms directly. Total product effect and cache/model
   effects must not be confused.
5. Repeat the frozen holdout on the second subscription provider. A result on
   Claude is not evidence of the same gain on Codex. Publish exact metadata,
   protocol/configuration hashes, all failures, exclusions and analysis code.

Unit of inference is the independently initialized episode, not its requests,
dependent task segments, or repeated seeds. Cluster repeats by episode family;
use a pre-specified paired cluster bootstrap (fixed seed, 10,000 replicates) for
intervals. Existing exhaustive 2^n analysis is unsuitable above 20 pairs; retain
it for its historical schema, add a versioned analyzer. Do not silently drop
expensive failures. Incomplete accounting blocks a complete-evidence claim.

## Delivery sequence

| Milestone | Shippable result | Exit condition |
| --- | --- | --- |
| 2.2-alpha.1 | Complete-cost ledger and explicit multi-unit packets | Offline reconciliation and grouping tests; v2.1 compatibility |
| 2.2-alpha.2 | Freshness-bound context packets and local test/diagnostic helpers | Changed-input invalidation and full-output recovery pass |
| Calibration | Small same-model paired pilot | Positive usable signal or explicit stop/redesign decision |
| 2.2-rc | Frozen packet policy and reproduction harness | Held-out token/quality/latency results and ablations |
| 2.2 stable | Proven workload-specific mode, easy opt-out | Cross-provider scope stated honestly; unsupported tasks native |

Do not couple publication of safety/measurement improvements to a positive
savings finding. Conversely, green tests alone do not enable a savings badge.
The technical moat is the verified relation between tasks, facts, actions and
measured outcomes—not the amount of framework code or the word “epistemic”.
