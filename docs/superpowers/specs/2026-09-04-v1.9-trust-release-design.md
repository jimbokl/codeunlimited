# codeunlimited 1.9 Trust Release Design

**Date:** 2026-09-04
**Status:** Approved for autonomous implementation
**Base:** `origin/main` at `f77befc410403abf8b11fa36dd56e7f3dd5cf589`

## Goal

Ship version 1.9.0 as a release whose safety and token-efficiency claims are
reproducible. The release must preserve user-authored instruction files,
distinguish exact observed counters from modeled counterfactuals, publish
negative experiment results without invalid significance claims, and install
only checksummed binaries.

## Product position

codeunlimited is an offline diagnostic and workflow-policy tool. It can show
where large contexts, retries, cache rewrites, and heavy session starts consume
tokens. It does not guarantee a fixed percentage of subscription savings.
Realized savings are an outcome metric: input tokens per comparable completed
task, with quality and completion held constant.

The 1.9 headline is therefore “measure first, change safely, verify the
outcome.” The historical `x6.8` result remains a useful illustration of modeled
context-growth exposure, but is not described as realized or exact savings.

## Considered approaches

1. **Documentation-only correction.** Fast, but leaves destructive block
   migration, fail-open installers, and false-green CI. Rejected.
2. **Trust-first hardening across the existing boundaries.** Keep the Rust CLI
   and stdlib Python evidence harness, repair each contract with focused tests,
   and release 1.9.0. Selected.
3. **Rewrite all measurement in Rust.** A cleaner long-term consolidation, but
   it expands the release surface without improving the historical evidence.
   Deferred until after 1.9.

## Safe instruction-block upgrades

`initcmd::upsert_block` becomes fallible. A file is mutated only when it has:

- no codeunlimited markers;
- exactly one complete v2 start/end marker pair in the correct order; or
- exactly one legacy v1 marker immediately followed by the known
  `## Token efficiency (codeunlimited)` heading.

Orphan markers, duplicate blocks, reversed markers, and malformed legacy
blocks return an invalid-data error and leave the file byte-identical. A valid
legacy block extends from its marker through the content before the next level-2
heading, or through EOF when it is the final section. Surrounding bytes and the
file's LF/CRLF convention are preserved. Existing safeio backup and symlink
protections remain in force.

## Context-tax benchmark semantics

`scripts/bench_context.py` becomes an importable, tested CLI with `--root`,
`--min-turns`, `--early-turns`, and `--json` options. Its default root is
`Path.home() / ".claude" / "projects"` on every platform.

For every session with strictly more than `min-turns` recognized assistant
records:

- `actual_prompt_tokens` is an exact sum of recognized integer counters;
- `modeled_bounded_prompt_tokens` is `first-N mean × request count` and is
  explicitly counterfactual;
- `modeled_difference_tokens` may be positive, zero, or negative;
- no session is excluded because its modeled result is unfavorable.

Malformed candidate records are counted. Unreadable files fail the run. Missing
roots fail with a useful diagnostic instead of returning a zero-looking result.
Default output is aggregate and does not expose project names, session IDs,
paths, prompts, responses, or models. JSON contains a schema version, method
parameters, exact observed totals, modeled totals, included-session counts, and
accounting-completeness fields.

## Experiment evidence

The existing controlled A/B is retained as a descriptive aggregate result:
the treatment used 1.08M prompt tokens versus 0.92M for control, approximately
17.4% more. The request-level Mann–Whitney p-value is removed because requests
within a session are not independent experimental units.

A new stdlib-only paired-task analyzer accepts explicit task-level control and
treatment totals. It reports exact aggregate totals, per-task differences,
request medians, and an exact two-sided sign-flip permutation p-value across
paired tasks. It refuses duplicate/missing task pairs, non-integer or negative
counters, and fewer than two pairs. No task-level dataset is fabricated for the
historical experiment; the documentation states that statistical significance
cannot be independently reproduced until those observations are published.

The v1.7/v1.8 evidence validator is bounded by an explicit v1.8 release commit,
not the moving `HEAD`. CI fetches the history needed to verify that provenance.

## Installer contract

Both installers download the binary and its `.sha256` file before touching the
installed executable. Missing, malformed, unavailable, or mismatching checksum
data is fatal. The downloaded binary is smoke-tested with `--version`, staged
on the destination filesystem, and then moved into place. Failed installs
preserve the previously installed binary.

`CODEUNLIMITED_DOWNLOAD_BASE_URL` is a documented testing/mirror override.
`CODEUNLIMITED_INSTALL_DIR` remains the destination override. Unix installers
do not edit shell profiles; they accurately report whether the chosen directory
is already on PATH and print the required export otherwise. PowerShell updates
the user PATH idempotently after a verified installation.

## CI and release contract

CI explicitly discovers `tests/test_*.py`, runs the benchmark/release suites on
Python 3.10 and 3.12, exercises the Unix installer against a local fixture on
Linux, and exercises the PowerShell installer on Windows. The Python job uses
full git history for provenance validation. Package metadata, release workflow,
Cargo manifest/lockfile, changelog, and documentation all agree on `1.9.0`.

The release gate is:

1. formatting and clippy with warnings denied;
2. all Rust tests on Linux, macOS, and Windows;
3. Rust 1.82 MSRV check;
4. all Python evidence and installer tests;
5. release metadata, package audit, and exact packaged-source smoke test;
6. generated Linux, macOS, and Windows artifacts with mandatory checksums;
7. live installer verification only after the GitHub release is available.

## Documentation and claims

README, benchmark, experiment, accuracy, roadmap, changelog, and launch copy use
the same vocabulary:

- **exact observed**: an integer sum over recognized records;
- **modeled**: a counterfactual based on declared assumptions;
- **estimated reclaimable**: detector output with documented ranges;
- **realized outcome**: a comparable-task before/after observation;
- **causal**: never claimed by current evidence.

The repository description and launch copy must not promise “up to 50%” or
describe the modeled `x6.8` exposure as realized savings.

## Acceptance criteria

- Malformed, duplicate, orphaned, or mixed block markers cannot change an
  instruction file; valid v1/v2 updates remain idempotent on LF and CRLF files.
- Context-tax fixtures prove that unfavorable modeled sessions remain in the
  aggregate and that missing roots and malformed records are visible.
- The controlled A/B documentation reports the total-token loss and contains no
  request-level significance claim.
- The paired analyzer's exact p-value is derived from task-level pairs and has
  hand-checked deterministic tests.
- Missing or bad checksums fail before replacing an existing binary.
- CI runs the test that previously failed outside GitHub discovery.
- `codeunlimited techniques` is present in the packaged 1.9.0 binary.
- Every public savings claim can be mapped to a checked-in method and evidence
  level; no fixed realized-savings percentage is promised.

## Non-goals

- Reconstructing unpublished historical request/task data.
- Claiming causality from the existing experiments.
- Editing model or MCP configuration automatically.
- Adding telemetry, network services, API keys, or prompt-content analysis.
- Replacing the Rust CLI with the Python evidence harness.
