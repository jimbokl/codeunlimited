# codeunlimited 2.1 Subscription-First Cache Architecture

**Date:** 2026-09-04
**Status:** Approved for autonomous implementation
**Base:** `codex/v2-state-runtime` at `f4b8bbd8552672bbbe04afc7a463155ca0604d6e`

## Goal

Version 2.1 must reduce repeated input for long coding work through two explicit,
non-interchangeable execution layers:

1. **Primary: subscription CLIs.** Claude Code and Codex keep using the user's
   existing subscription login. codeunlimited bounds cross-step state and sends
   invariant instructions through an additive Claude instruction channel or a
   Codex ordered-read bootstrap. Claude stdin contains changing state and the
   latest observation; Codex stdin is the constant file-read bootstrap.
2. **Secondary: external APIs.** Optional OpenAI and Anthropic adapters use API
   keys from the environment, explicit provider cache controls, and separate
   metered accounting. They are not required for the main product path.

The release must report observed usage counters without converting subscription
usage into fictional API dollars or promising a cache hit that the provider did
not report.

## Why 2.0 left savings on the table

2.0 concatenates the stable workflow and changing state into one stdin message.
That bounds history, but it does not create a stable provider message boundary.
Public provider caches match exact prefixes at provider-defined boundaries; a
changing tail inside the same message can prevent reuse. 2.0 also repeats the
full structured-output schema both in the text prompt and in each built-in
CLI's schema flag.

2.1 separates transport channels. The stable bytes are immutable for a run and
are written once to `provider-instructions.md`; built-in CLIs receive that file
as their instruction source. The dynamic stdin message contains only the
current state, latest observation, their digests, and the revision. The command
adapter remains self-contained and receives the combined prompt because its
protocol is intentionally generic.

## Considered approaches

### Subscription-only wrapper

This has the smallest security surface and directly serves the primary use
case, but cannot expose explicit API cache breakpoints or cost telemetry. It is
the primary layer, not the complete 2.1 architecture.

### API-first coding-agent replacement

This provides direct cache controls, but it would make API spend and a new tool
sandbox mandatory. It contradicts the product's subscription-first purpose and
would conflate transport savings with a second agent implementation. Rejected
as the default.

### Shared prompt compiler with separate transports

One compiler emits immutable and dynamic channels. Subscription adapters place
them through CLI-native instruction mechanisms. Optional API adapters place an
explicit cache breakpoint after the stable channel. Usage normalization keeps
provider-native raw fields. Selected.

## Layer 1: subscription CLI runtime

`ProviderConfig::Claude` and `ProviderConfig::Codex` gain a
`subscription_profile` field. Existing v2.0 manifests deserialize with the
`standard` default.

Profiles:

- `standard` changes only prompt placement and preserves the user's normal CLI
  configuration.
- `lean` additionally disables nonessential dynamic integrations so repeated
  hidden tool/config material is smaller and more stable. It remains opt-in
  because a reduced tool surface can change agent capability.

Claude invocation:

```text
claude --print --no-session-persistence --output-format json
  --json-schema <StepEnvelope schema>
  --append-system-prompt-file <immutable provider-instructions.md>
  --exclude-dynamic-system-prompt-sections
  [lean isolation flags]
```

Codex invocation:

```text
codex exec --ephemeral --json --cd <project>
  --output-schema <temporary schema file>
  --output-last-message <temporary output file>
  [lean isolation flags]
```

The Codex CLI currently exposes no file-backed *additive* developer-instruction
flag. Its `model_instructions_file` setting replaces built-in instructions, so
2.1 does not use it. Replacing Codex's tool and safety contract merely to improve
caching would be a quality regression. Instead Codex receives a short immutable
bootstrap prompt naming three project-relative files and requiring separate,
ordered reads: `provider-instructions.md` first, then `state.json`, then
`observation.txt`. This preserves Codex and `AGENTS.md` behavior while moving
the large stable workflow ahead of the changing tool results in the worker's
turn sequence. The bootstrap bytes are identical across run revisions. The
ordering is tested at the adapter boundary but remains an instruction to the
provider, not a proof that its internal cache retained the tool-result prefix.

Lean mode never uses Claude `--bare`, because that disables subscription OAuth.
It disables slash commands, Chrome integration, and unapproved MCP servers and
restricts Claude's built-in tools to the coding set. Codex lean mode uses
`--ignore-user-config`; authentication is still loaded from `CODEX_HOME`.
Project rules remain a native CLI responsibility, not a duplicate AGENTS.md
snapshot in the immutable instruction file.

The runtime writes no provider credential. Every step still starts a fresh
process, never passes a continuation ID, and carries no provider transcript.

## Layer 2: optional external APIs

The API layer is configured with `openai-api` or `anthropic-api` and is compiled
into the same binary, but is never selected implicitly. Manifests persist only
endpoint/model/cache-policy configuration and the name of the environment
variable containing the key. The key value is read only for an invocation and
is never serialized, logged, included in an error, or passed in argv.

OpenAI requests put the invariant contract in a developer content block and
mark its end with an explicit prompt-cache breakpoint. They send the dynamic
state as the following user block, use a stable cache key derived from the
instruction hash, and request strict JSON-schema output. Anthropic requests put
the invariant contract in a system block with ephemeral cache control and send
the state as the following user message. The cache TTL is provider-specific and
validated before the request.

The API execution layer in 2.1 is deliberately **single-turn orchestration**:
it requests a `StepEnvelope` and does not expose local file or shell tools.
Consequently it is useful for planning, state reduction, and workflows whose
external action is performed by a verification command, but it is not claimed
as a drop-in coding-agent replacement. A capability field in status makes this
distinction visible. A future release may add a separately audited tool
sandbox without changing the prompt channels.

Default endpoints are HTTPS provider endpoints. A custom HTTP endpoint is
accepted only when it is loopback, enabling deterministic local tests; remote
plain HTTP is rejected.

## Prompt artifacts and budgets

Each run stores:

```text
.codeunlimited/runs/<name>/
  manifest.json
  workflow.md
  provider-instructions.md
  state.json
  observation.txt
  ...
```

The stable file contains the runtime contract, workflow digest and bytes,
objective, and a concise instruction
that the provider-specific schema is authoritative. It does not duplicate the
schema body for built-in/API adapters. The combined command prompt includes the
schema because no out-of-band schema channel can be assumed.

`CompiledPrompt` exposes `stable`, `dynamic`, and `combined` bytes and hashes.
All three are checked before invocation. Status shows their exact byte sizes.
The stable hash must remain identical for every revision of a run.

## Usage semantics and evidence

Raw counters are persisted per attempt:

- total input tokens when the provider reports them;
- uncached input tokens when the provider reports them;
- cache-read input tokens;
- cache-write input tokens, including separate 5-minute and 1-hour Anthropic
  fields when present;
- output tokens.

The normalized ledger also derives `transported_input_tokens` only when the
provider's documented counter semantics make that calculation unambiguous.
OpenAI's input total already includes cached input; Anthropic's `input_tokens`
is the uncached remainder and is added to cache reads and writes. Unknown
semantics remain `null`, never zero.

`run status` reports raw totals and a cache read ratio when it is derivable.
`run cache-probe` is an explicit, opt-in command that performs two small fresh
provider calls using the run's stable instructions and two dynamic nonces. It
reports the two raw usage records, whether the second call has a reported cache
read, and the stable hash. It never runs automatically. Probes force reduced
integrations and no-op inputs, with a 60-second cap per call; they are not an
exact replay of a standard-profile coding workload. Reported reads may belong
to the provider's own system prefix. Probe usage is separate from step totals.

For subscription CLIs, economic savings are established only by a paired
workload benchmark with provider-reported counters. Public API price
multipliers are not applied. For API providers, callers may calculate cost from
the raw counters and current provider prices outside the runtime.

## Configuration and compatibility

Implementation decision: retain manifest/state/envelope schema version 1 and
add compatible defaults rather than unnecessarily coupling a manifest version
bump to every state/envelope. Missing `subscription_profile` defaults to
standard. Legacy missing instructions are generated in memory; `status` and
`prompt` do not rewrite the manifest or instructions. The first execution
materializes the instruction file. Inspection remains available for a tight
legacy prompt budget; execution still enforces that budget before invocation.

New CLI inputs:

```text
--subscription-profile standard|lean
--api-model <MODEL>
--api-endpoint <HTTPS_OR_LOOPBACK_URL>
--api-key-env <ENV_NAME>
--cache-ttl 5m|30m|1h
```

Provider-invalid combinations fail at `init`. Status redacts provider arguments.
API key-variable names and values are omitted from status output.

## Security and failure behavior

- No shell is used for provider or verification commands.
- Stable instruction paths are regular files inside the symlink-checked run
  directory.
- Provider flags that can replace required output, instruction, cache, auth, or
  continuation behavior are rejected.
- HTTP response bodies, authorization headers, and provider stderr are never
  included in user-facing failures or attempt journals.
- HTTP bodies share the existing 1 MiB response cap and provider timeout.
- Network/API failures do not advance state. Ambiguous repository-change rules
  remain identical to 2.0.
- Cache misses are normal results, not runtime errors.

## Tests and release evidence

All production behavior is developed test-first. Tests must prove:

- stable instruction bytes and hashes do not change across revisions;
- built-in stdin contains no workflow, objective, project instructions, or
  duplicated JSON schema;
- command-provider stdin remains self-contained;
- Claude and Codex argv contains exactly one stable instruction source and
  rejects overrides;
- standard and lean profiles differ only by the documented flags;
- v1 manifests load without mutation and acquire standard behavior;
- OpenAI and Anthropic request builders place cache boundaries correctly;
- local mock HTTP servers validate headers, JSON, parsing, size limits, error
  redaction, and usage semantics without a live model call;
- cache-probe output is honest for hit, miss, and unavailable counters;
- Rust 1.82, clippy, release tests, Python reference tests, packaging, and audit
  gates stay green.

## Honest 2.1 claim

codeunlimited 2.1 mechanically bounds cross-step context and aligns invariant
content with the strongest cache boundary available in the chosen transport.
It can materially reduce repeated input when a provider reports reuse. It does
not control hidden subscription system prompts, guarantee cache retention,
guarantee that compact state preserves all task quality, or promise the
five-times result of a different workload and architecture.
