# v2.2 delivery: explicit work packets and complete-attempt accounting

Date: 2026-09-04. Target: 2.2.0. Owner authorized autonomous delivery.
Baseline: v2.1 merged main plus the separately labelled offline DCR research.

## Decision and release boundary

Ship a bounded, opt-in work-packet mode on the existing subscription-first
runtime and an inspectable all-attempt ledger. This is an architectural change.
It implements the first milestone of the adaptive-work roadmap; it does not
implement a learned scheduler, automatic source-context compression, test-result
reuse, or a replacement agent. API adapters remain separate and unchanged.

Alternatives considered: more API cache tuning cannot establish subscription
savings; speculative DCR promotion has no demonstrated advantage over a script;
explicit grouping removes a concrete repeated-start boundary without another
model call. Select explicit grouping, with native legacy mode retained.

The broad roadmap's evidence gate still controls any default-on optimization or
savings claim. Version 2.2.0 may ship the opt-in mechanism and safety/accounting
improvements with **realized token savings unproven**. No live provider benchmark
is authorized by this plan. Local fixture counters are not real model usage.

## Global constraints

- Rust 1.82 and Python 3.10 remain supported; no new third-party dependencies.
- Preserve v2.1 run readability and legacy no-plan prompt/instruction bytes.
- No global configuration, permission changes, live model calls, or API spend.
- No implicit acceptance, fabricated usage, hidden failures, or savings badge.
- Runtime limits are UTF-8 bytes, not token estimates.
- Keep all work in the existing external-drive worktree; preserve unrelated changes.

## 1. Attempt journal and ledger

Before invoking a provider, atomically create an intent containing the attempt
number, base revision, provider kind, prompt/config digests and start timestamp.
An interrupted intent is visible after process death; a new worker must not be
started until explicit recovery. Finalization writes an immutable attempt record
before clearing its intent. Recovery of an unmatched intent records unknown usage,
preserves repository edits, and consumes the attempt cap. If a final record is
already present, recovery must reconcile it without creating a duplicate charge.
Never silently remove unresolved intents. Inspect/status/ledger are read-only.

Add `run ledger NAME --project PATH [--json]`. JSON schema 1 contains run/provider,
configuration digest, per-attempt metadata/counters, and aggregate coverage.
For every attempt normalize transported input independently before summing;
cache reads/writes must not be added twice. Report observed input/output subtotals,
counts of complete/incomplete attempts, and nullable complete total tokens.
One unknown attempt makes complete total null, not zero. Overflow also invalidates
the total. Zero attempts is explicitly no evidence. Busy/pending runs cannot claim
complete accounting. Coverage describes reported worker-attempt counters, not an
audit of hidden provider internals or subscription quota. Cache probes stay outside
step accounting and are explicitly identified as excluded.

Optional `run init --max-total-tokens N` is a soft boundary admission limit. Once
complete observed total reaches N, do not start another worker. After an attempt
with unavailable usage, stop admission under this option; never treat unknown as
zero. The first attempt is allowed; overshoot by a running worker is reported,
not prevented by killing it. No configured cap preserves existing behavior.

Expose accepted task IDs only when explicitly planned and verified by the frozen
acceptance command. Ledger tokens/accepted-task is null for zero accepted tasks,
partial accounting, or a run without declared task contracts. Failed attempts
always remain in the numerator. No comparison or percent-saving field is inferred.

## 2. Immutable work contracts and deterministic packets

`run init --work-plan FILE` reads a bounded regular JSON file and snapshots its
contents in the manifest. It is opt-in; no user-authored plan means v2.1 behavior.
Schema:

```json
{"schema_version":1,"max_packet_tasks":4,"tasks":[
  {"id":"a","task":"Update parser fixture","group":"parser","depends_on":[],"scope":["tests/parser.rs"],"risk":"low"},
  {"id":"b","task":"Update parser error case","group":"parser","depends_on":["a"],"scope":["tests/parser.rs"],"risk":"low"}
]}
```

Limits: 32 tasks, 1..8 tasks per packet, 32 KiB plan file, 512-byte task text,
16 scope paths per task. IDs/groups use existing safe ID validation. Risk enum:
low, medium, high. Scope consists of safe project-relative file paths; it is
planning metadata, not an OS sandbox or authorization to bypass provider checks.
Reject duplicate IDs/dependencies/paths, unknown dependencies, cycles, unknown
fields, empty task/group/scope, unsafe paths and out-of-range budgets before any
run directory/provider call. Require a verification command; disallow unverified
completion. All packets use this one frozen full acceptance command.

Seed state.queue from the immutable plan. Select the first remaining ready task
in declaration order, then repeatedly select ready tasks of the same group, same
risk and identical scope set until the packet cap. A dependency is ready if
completed in an earlier accepted transition or earlier in the current packet.
Never infer grouping from string similarity. Different metadata splits packets.
Expose `run packet NAME --project PATH [--json]` for a no-call preview with selected
IDs, reason, and remaining count. No ready task is a validation error, never a spin.

All provider transports receive identical packet IDs/tasks/order/scope. Generic
and Claude get the packet in dynamic context; Codex gets the same data in its
bootstrap after the existing ordered input reads. Do not change legacy stable
instructions. Managed-plan instructions explicitly require dependency order and
completion of only selected tasks, with one structured response per packet.

Validate the response before committing: completed_add must be a nonempty prefix
of selected packet IDs, except explicit blocked outcomes may complete none;
queue cannot add, rewrite, reorder, or silently drop planned tasks. Derive expected
remaining queue from the plan/completed set and reject conflicting queue_replace;
when omitted, runtime sets it. No duplicate, fabricated, outside-packet completion.
Previously accepted IDs cannot be revised. Completion requires all tasks accepted.
Run full frozen verification on every managed packet; failed checks accept no tasks
and preserve failure evidence/usage through existing recovery behavior. Passing
checks mean acceptance under the configured suite, not proof of semantic quality.
The runtime freezes the verification program/argv, not the contents of mutable
repository tests or the executable's environment. Stronger acceptance requires a
trusted verifier outside the worker-editable scope. Offline comparisons must also
independently assert the requested final tree, not just trust a worker's IDs.

Cap plans at 32 tasks so accepted IDs remain in the existing bounded completed
state; do not introduce a second mutable source of task truth or rely on archives.
Use additive defaulted fields for manifest/attempt compatibility. Old binaries
need not read newly configured runs; existing runs remain readable by 2.2.

## 3. Offline evidence, docs and release

Provide a reproducible local subprocess demonstration using the actual Rust CLI:
four literal file-edit tasks and one frozen acceptance script, once with packet
cap 1, once with cap 4. Both produce the same accepted files. Record actual worker
process counts, attempts, acceptance and prompt bytes; provider/model calls and
real token savings remain unavailable. Include wrong completion, verification
failure, interrupted attempt, unknown counters and cap admission tests. Use a
deterministic scripted worker, never launch Claude/Codex/OpenAI/Anthropic.

The expected 4-to-1 process boundary reduction is a mechanism test, not a competent
native-agent comparison. Record this caveat next to results, not only in a footnote.
DCR remains research-only. Native whole-objective workflows may already batch as
well or better; larger packets may increase repair cost.

Update Cargo metadata, release checks, CI version references, changelog, README,
runtime documentation and VERSION-2.2.md. Validate fmt, clippy, all Rust/Python
tests, locked package build and archive contents/tests. Use isolated offline
fixtures. Public hosting/merge/tag actions require explicit authorization; prepare
a clean release branch and handoff without publishing a stable savings claim.
