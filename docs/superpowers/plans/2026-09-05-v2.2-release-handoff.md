## Delivered

- Opt-in immutable work plans and deterministic bounded task packets. No
  scheduler model call; legacy no-plan behavior remains available.
- Durable pre-dispatch intents, immutable attempt records, and read-only ledger
  coverage. Failures and unknown usage remain visible, not zeroed or dropped.
- Optional total-token admission cap. It controls the next call, cannot stop an
  ongoing call, and reports known overshoot.
- Managed acceptance requires an ordered task prefix and the configured frozen
  verification command. Final acceptance must explicitly return Complete.
- Recovery preserves a terminal transition already committed before final
  attempt-record failure. Missing usage remains unknown even when state is
  committed; recovery does not invent accepted-task accounting.
- Offline mechanism demonstration, release documentation, CI prerequisites,
  package inclusion/privacy checks, and version metadata at 2.2.0.

The separate external API layer was not expanded. No global configuration,
permission changes, live provider benchmark, API spend, push, tag, shared-branch
merge, or release publication was performed in this delivery. Development and
review agents did use model tokens; that is separate from the offline benchmark.

## Decisions, costs and product verdict

Packets remain opt-in. Four-to-one fixture starts do not establish fewer model
requests, transported tokens, or subscription-quota use. All real-token totals
and savings percentages remain null; a competent native-agent comparison was
not run. Larger packets may increase repair costs and planning overhead. Scope
paths are metadata, not a sandbox; a frozen verifier command does not make
mutable test files immutable or prove every aspect of semantic quality.

Explicit final Complete acceptance prevents a terminal empty-queue dead end but
may require a repair attempt when a worker emits the wrong outcome. Conservative
recovery preserves unknown accounting rather than estimating a favorable total.
Keeping this release local leaves a separate publication step.

Position 2.2 as a controlled stateful runtime with auditable attempt accounting
and experimental token-efficiency mechanisms, not a proven subscription-token
saver or a scientific discovery. Before a default-on recommendation, separately
authorize a matched-quality native-agent comparison over increasing horizons,
including setup, failures, repairs and every attempt. Where the client does not
expose subscription allowance attribution, do not substitute API discounts.

The additional supplied analysis is reviewed in
[the research note](../../research/2026-09-04-supplied-token-methods-review.md).
Its useful technique inventory does not validate its general savings ranges or
justify adding a compressor or semantic response cache to this release.
